droidBSD

An experimental BSD-based operating system for mobile phones.

Genuine BSD userspace on mobile hardware — without rewriting every driver from scratch.

⚠️ Experimental Project — High Risk

droidBSD is experimental software. Installing or testing it can permanently damage (“brick”) your device. Always back up data and test thoroughly before any permanent installation. Proceed at your own risk.

What is droidBSD?

droidBSD is an experimental project that aims to bring a genuine BSD operating-system environment to mobile phones.

The project does not try to create a completely independent hardware support stack from scratch. Instead, it deliberately reuses the existing Linux kernel and hardware support already present on many Android devices. This dramatically reduces the amount of reverse-engineering and driver work required in the early stages.

Core idea

Android itself is not the user-facing operating system. The Android userspace (ART, Zygote, the traditional Android application stack, Google Apps, and related components) is intended to be removed or replaced. What remains is the Linux kernel acting as a low-level compatibility and hardware-support layer underneath a FreeBSD-based userspace.

Conceptual stack

Hardware (phone SoC, display, radios, etc.)
↓
Existing Linux kernel + device drivers / firmware
↓
Compatibility / bridge layer
↓
droidBSD (FreeBSD-based userland + system components)
ℹ Important distinction

droidBSD is not “BSD running inside Android.” The goal is to replace the Android userspace, not to run as an application or container on top of a full Android system.

Why this approach?

Writing complete, independent hardware support for modern mobile SoCs is an enormous undertaking. By reusing kernels and drivers that already understand a given phone’s hardware, the project can focus on the userspace, system services, and user experience much earlier.

A fully independent / bare-metal implementation remains a long-term aspiration, but it is not the current practical path.

Project Goals

Primary goals

  • Provide a genuine BSD userland (shell, utilities, system tools, services) on mobile hardware.
  • Replace the Android userspace rather than merely theming or modifying it.
  • Reuse existing Linux kernel and hardware support to make early development feasible.
  • Develop tools (especially libdt) that help adapt system images to different devices with less manual work.
  • Offer a lightweight, purpose-built graphical interface suitable for phones.

Non-goals (current phase)

  • Claiming universal compatibility with every Android phone.
  • Pretending that a full bare-metal port already exists.
  • Running the full Android application stack or Google services.
  • Providing production-ready daily-driver images at this stage.

Long-term direction

Over time the project may move toward greater independence from the Linux kernel and Android-era components. That path is acknowledged as desirable but is deliberately secondary to making a usable BSD environment available on real hardware first.

ℹ Honesty policy

Features that are not yet implemented are clearly marked as Planned, Experimental, Under development, or Device-dependent.

Architecture Overview

droidBSD is structured as a layered system that deliberately separates hardware support from the BSD userspace.

High-level view

Hardware │ ▼ ┌─────────────────────────────────────┐ │ Linux kernel + existing drivers │ │ (display, touch, Wi-Fi, storage…) │ └─────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────┐ │ Compatibility / bridge layer │ │ (libdt adaptations, possible │ │ hybris-style components for GPU) │ └─────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────┐ │ droidBSD │ │ • FreeBSD-based userland │ │ • Custom init & services │ │ • Graphical interface │ └─────────────────────────────────────┘

Key principles

  • Reuse where it saves years of work — the Linux kernel already knows how to talk to the phone’s hardware on many devices.
  • Replace the userspace — ART, Zygote, and the classic Android app stack are not part of the intended droidBSD environment.
  • Adapt rather than hard-code — libdt is intended to inspect device information and adapt the system image instead of requiring a fully hand-written port for every phone.
  • Be explicit about limitations — proprietary firmware, bootloader behavior, GPU stacks, and many other factors can still block support.

How It Works

The intended high-level workflow for bringing droidBSD to a device is:

  1. Identify the device — determine model, SoC, and available kernel / device-tree information.
  2. Back up important data — always.
  3. Extract / inspect hardware information — Device Tree, kernel configuration, and related data.
  4. Let libdt prepare / adapt the system image — Under development
  5. Test using a temporary / non-permanent method — Device-dependent / Planned
  6. Verify boot and critical hardware — display, touch, storage, networking, etc.
  7. Only then consider permanent installation — after successful testing.
⚠ Temporary testing methods

Specific temporary boot mechanisms (fastboot boot, recovery-based testing, ramdisk approaches, etc.) are device-dependent and still under definition. The documentation will not invent a single universal method. Always follow device-specific guidance when it becomes available.

This workflow is designed to minimize the risk of permanent damage during early experimentation.

Linux Kernel Layer

On supported target devices the existing Linux kernel is retained as the foundation.

Why keep the Linux kernel?

  • It already contains drivers and configuration for the phone’s display controller, touchscreen, storage, Wi-Fi, Bluetooth, power management, and other hardware.
  • Creating equivalent support from scratch for modern mobile SoCs is a multi-year effort for each platform family.
  • Using a known-working kernel lets the project concentrate on userspace and system design.

What the kernel provides

  • Hardware abstraction and device drivers
  • Process scheduling, memory management, and system-call interface
  • Filesystem support and storage access
  • Networking stack
  • Power-management interfaces (to the extent implemented by the vendor kernel)
ℹ Scope

Exact hardware support varies by device and by the particular kernel build shipped with that device (or community ports of it). droidBSD does not magically add missing drivers.

libdt

libdt is a component under development whose purpose is to inspect a target device’s hardware information and adapt a droidBSD system image accordingly.

Intended responsibilities

  • Read and interpret Device Tree data (and related kernel / device configuration).
  • Detect relevant hardware characteristics of the phone.
  • Patch or generate device-specific configuration for the droidBSD image.
  • Help produce a system that can be tested on that particular device with less manual porting work.

What libdt is not

  • It is not a guarantee of compatibility with every phone.
  • It cannot overcome missing proprietary firmware, incompatible bootloaders, or fundamental hardware differences.
  • It does not eliminate the need for testing and possible manual adjustments.
⚠ Status

libdt is Under development. Its exact interfaces, capabilities, and limitations will be documented as the implementation matures. Do not assume any particular automation feature is already complete.

Device Tree & Hardware Detection

Most modern ARM-based mobile devices describe their hardware using a Device Tree (DT). The Device Tree Blob (DTB) and related source (DTS) tell the kernel which peripherals exist, how they are connected, and which drivers should bind to them.

Role in droidBSD

Because droidBSD reuses an existing Linux kernel, the Device Tree that already works with that kernel is a primary source of hardware information. libdt is intended to consume this information (and other available configuration) so that the higher-level system can be adapted without writing a full board-support package by hand for every phone.

Limitations

  • Not every relevant detail is always present or accurate in the Device Tree.
  • Proprietary firmware, closed-source driver modules, and bootloader constraints live outside the DT.
  • Different kernel versions and vendor trees can expose different interfaces.

Hardware detection and adaptation remain Device-dependent and Experimental.

GPU / Compatibility Layer

Graphics on mobile SoCs are frequently tied to proprietary user-space components and interfaces that were designed around Android.

Approach

When necessary, a compatibility layer inspired by projects such as libhybris may be used. The goal is to allow existing low-level hardware components (especially GPU-related) to communicate with the non-Android userspace, without bringing up the entire Android operating system.

ℹ Clarification

This is reuse of selected low-level binary components and interfaces, not “running Android.” The Android application framework, ART, and related userspace services are not part of the intended droidBSD stack.

Exact support for accelerated graphics is Device-dependent and currently Experimental / Planned.

BSD Userspace

The userspace is intended to be genuine BSD software, primarily based on FreeBSD components and conventions.

Expected components

  • BSD shell (e.g. sh / tcsh or similar)
  • Standard BSD userland utilities
  • System administration tools
  • Custom droidBSD services
  • A custom initialization process (not Android’s Zygote / ART startup)
  • A custom graphical interface

The project aims to replace the Android userspace rather than simply put a different interface on top of Android’s existing services.

ℹ Status

Userspace integration, service design, and the precise set of packages are still under active development. Many pieces remain Planned or Experimental.

Boot Process

In a finished system, droidBSD will start its own initialization and userspace environment instead of the normal Android boot path that leads to Zygote and ART.

Technical difficulty

Changing the boot → userspace transition on a phone is technically difficult and potentially dangerous, especially while the project is still experimental. Bootloader constraints, verified-boot mechanisms, partition layouts, and initramfs / ramdisk handling all vary by device.

⚠ Risk

Incorrect changes to the boot process can render a device unbootable. Always prefer temporary testing methods before any permanent modification of boot partitions.

Details of the final init system and early boot sequence are Under development and will be documented as they stabilize.

Graphical Interface

droidBSD will include its own lightweight graphical interface designed for mobile hardware.

  • It may share some visual conventions with mobile systems (status bar, navigation gestures, etc.) because the target form factor is a phone.
  • It is not Android and should not be presented as a reskinned Android UI.
  • The exact toolkit, compositor, and application model are still being defined.

Status: Planned / Experimental.

Device Compatibility

droidBSD explicitly does not guarantee compatibility with every Android phone.

Mobile hardware varies widely even among devices that use similar CPU architectures. Possible obstacles include:

  • SoC differences
  • GPU differences and proprietary graphics stacks
  • Proprietary firmware blobs
  • Kernel version and configuration differences
  • Device Tree differences
  • Display controllers and panel initialization
  • Touchscreen hardware and firmware
  • Wi-Fi / Bluetooth chips
  • Storage (eMMC / UFS) configuration
  • Bootloader behavior and unlocking restrictions
  • Power-management hardware and drivers
  • Camera hardware and ISP pipelines
  • Vendor-specific closed-source drivers
Berry’s tip: “If the cheese doesn’t fit the hole, forcing it usually makes a mess. Same with phones.”

Community contributions that add support for additional devices are highly welcome. See the Contributing section.

Installation

🚨 Critical Warning

Experimental operating-system images can brick a device. Permanent installation should only be considered after successful temporary testing and after you fully understand the recovery options for your specific phone.

Recommended high-level workflow

  1. Identify the exact device model.
  2. Back up all important data.
  3. Extract and inspect the device’s hardware information (Device Tree, kernel, etc.).
  4. Use libdt (when available) to prepare / adapt a system image.
  5. Test the image with a temporary / non-destructive method.
  6. Verify that the device boots and that critical hardware functions.
  7. Only then consider permanent flashing.

Specific flashing commands, partition layouts, and recovery procedures are Device-dependent and will be documented per device when ready. No universal install script is claimed at this time.

Testing Before Flashing

Testing without permanently modifying the device is the safest way to evaluate compatibility.

Principles

  • Prefer methods that do not overwrite the main system or boot partitions until you are confident.
  • Have a known-working recovery / fastboot environment ready.
  • Document what works and what fails so the community can benefit.
⚠ Implementation status

Concrete temporary boot mechanisms are still being defined and will often be device-specific. They are marked Planned or Device-dependent until documented. Do not invent or assume a particular method (for example a universal “fastboot boot” workflow) unless it has been confirmed for that device.

Development

droidBSD is an open-source project in early experimental stages. Development currently focuses on:

  • The compatibility / bridge approach using existing Linux kernels
  • libdt and hardware adaptation tooling
  • BSD userspace integration
  • Early boot and init work
  • A lightweight graphical environment

Source repositories, issue trackers, and contribution guidelines will be published as the project infrastructure is set up. Until then, treat any code or images you encounter as highly experimental.

Troubleshooting

Because the project is experimental, most issues are currently expected rather than exceptional.

General advice

  • Confirm that a working Linux kernel and Device Tree already exist for your device.
  • Keep a known-good recovery or fastboot environment available.
  • Collect logs (kernel messages, early userspace output) whenever possible.
  • Search existing reports before assuming a unique problem.

Specific troubleshooting guides will be added as common failure modes are identified and documented.

FAQ

Is droidBSD just Android with a different UI? ▼

No. The goal is to replace the Android userspace (ART, Zygote, the normal Android application stack, etc.) with a FreeBSD-based environment. The Linux kernel is retained primarily as a hardware-support and compatibility layer.

Does it run Android apps? ▼

Running Android applications is not a current goal of the project. The intended userspace is BSD, not the Android application framework.

Will it work on my phone? ▼

There is no guarantee. Compatibility depends on many factors (kernel availability, Device Tree, proprietary components, bootloader, etc.). The project explicitly does not claim universal support.

Is there a full bare-metal version already? ▼

No. A more independent / bare-metal direction is a long-term aspiration. The current practical approach reuses existing Linux kernels and hardware support.

Can this brick my device? ▼

Yes. Experimental operating-system work on phones carries a real risk of permanent damage. Always back up data and prefer temporary testing methods before permanent installation.

Who is Berry? ▼

Berry is the official project mascot — a mouse who likes cheese. You will see Berry in non-critical sections of the documentation. Safety warnings remain completely serious.

Safety / Warnings

🚨 Read this carefully

Working with experimental operating-system images on mobile devices can result in a permanently unusable (“bricked”) phone. You accept full responsibility for any damage to your hardware, data loss, or other consequences.

Mandatory precautions

  • Back up all personal data before any experimentation.
  • Understand how to restore the original firmware on your specific device.
  • Prefer temporary / non-permanent testing methods whenever they exist.
  • Do not flash images to critical partitions until you have verified basic functionality.
  • Keep a working computer and the necessary cables / unlock tools available.

What the project does not provide

  • Any warranty or guarantee of safety
  • A universal unbrick method
  • Support for locked bootloaders or devices that cannot be recovered

If you are not comfortable with the risk of permanently losing a device, do not experiment with droidBSD images.
